## 1. 背景：纯 RAG 范式的六个根本问题

主流 RAG 知识库的范式是"**把文档切成 chunk，嵌入成向量，查询时按相似度捞取 top-k**"。这一范式在生产实践中暴露出六个层面的结构性问题：

| 层 | 问题 | 后果 |
|---|---|---|
| 切分层 | chunk 边界是任意的，语义边界不是 | 表格/代码/论证被肢解，指代悬空，粒度悖论无解 |
| 表示层 | 单向量无法承载多意图 | 精确匹配（编号、型号）失灵；否定、数字、时间被抹平 |
| 检索层 | 固定 top-k + 单次检索 | 多跳失败，全局问题不可用，新旧版本互相打架 |
| 组织层 | 知识是扁平的 chunk 池 | 无结构、无关系、无层级、无生命周期 |
| 治理层 | 更新=重切重嵌重建 | 知识只进不出，库越大越不敢动 |
| 工程层 | 串联黑盒，参数玄学 | bad case 无法归因，优化靠猜 |

**根本诊断**：纯 RAG 的问题不是"chunk 切得好不好"，而是"把知识压扁成无结构碎片、再靠相似度捞回"这一范式本身，丢弃了知识的结构、关系与生命周期。后续出现的各种补丁（混合检索、重排序、上下文化）都在缓解症状，没有触及病根。

## 2. 设计哲学：知识即构建

### 2.1 核心隐喻

KoiosBase 把知识库当作一个**持续构建的软件工程**来设计：

| 软件工程 | KoiosBase |
|---|---|
| 源代码仓库 | `raw/` —— 人维护的原始文档（Markdown Vault） |
| 编译器 | 编译层 —— 摄入时把源文档综合为结构化知识页（`wiki/`） |
| 构建产物/缓存 | `.index/` —— 向量、倒排、图索引，全部可重建 |
| 运行时 | 查询管线 —— 在构建产物上导航与推理 |
| 静态检查 / CI | lint 园丁 —— 周期性体检：矛盾、断链、失效、漂移 |
| 版本控制 | Git + 版本链 —— 一切变更可审计、可回滚 |
| 工程规范 | `AGENTS.md` —— 写在库里的维护契约 |

这个隐喻不是修辞，而是推导工具：**软件工程六十年积累的教训——源码是唯一真相、构建产物必须可再生、变更要增量、质量靠持续检查——对知识库全部成立。**

### 2.2 七条第一性原理

全系统的每个机制都从以下原理推导，不允许存在无法回溯到原理的"补丁式"组件：

**P1　Markdown 是唯一真相源。**
知识以人可读的 Markdown 持久化；一切索引都是派生物，删掉重建不丢任何知识。推论：任何无法从 Markdown 重新推导的数据不得写入索引。

**P2　存最细的，取任意粒度。**
存储单元是语义原子块（Block），chunk 不存在——检索结果只是 Block 之上按不同粒度生成的"视图"。粒度悖论（切小缺上下文、切大掺噪声）由此消解。

**P3　检索是导航与推理，不是相似度匹配。**
查询是一个迭代决策过程：规划意图 → 选择通道 → 评估充分性 → 改写或下钻。向量只是其中一条通道的召回器，从来不是裁判。

**P4　知识在摄入时综合，而不是查询时重推导。**
跨文档的实体、概念、综合知识由编译层**一次性物化并保持更新**；查询时直接取编译产物，而不是每次从碎片重新拼装。这让知识库产生"积累"——这是与纯 RAG 最本质的分野。

**P5　知识有状态，错误可传播式修正。**
每条知识有生命周期状态（active / superseded / disputed / retracted / draft）与置信度。一处错误被修正时，其影响面沿引用链可计算、可级联修复。

**P6　一切断言可审计到原文。**
任何输出的事实性句子必须携带到原文段落的引用；引用链穿透编译层直达 raw 层。引用不是功能，是契约。

**P7　判定者与生成者必须异源。**
系统中所有"判断对错"的环节（编译补丁、矛盾检测、Grader 充分性、lint 抽检）若与"生成内容"的环节使用同一模型家族，则构成闭环自证——同一模型对同源生成内容天然倾向判定为一致，draft 质量门防得住污染扩散，防不住这种一致性共谋。因此：能用程序化检查就不用模型；必须用模型时，判定模型与生成模型强制不同家族；判定分歧自动升级人工。

### 2.3 设计目标与非目标

**目标**（按优先级）：
1. 答案可信：可审计、可归因、证据不足时明确拒答；
2. 知识可积累：问答与摄入都在让库变得更好；
3. 单机轻量：万级文档、一台开发机可跑，无分布式依赖；
4. 可持续演化：解析器、模型、索引算法可独立替换升级。

**明确的非目标**（v1.0 不追求）：
- 不追求纯无向量路线（树搜索是通道之一，不是信仰）；
- 不追求重型知识图谱（只做实体级轻图，不做全量关系推理）；
- 不追求统一多模态向量空间（多模态走双轨制，见第 7 章）；
- 不追求替代人的判断（高风险修复永远进人工队列）。

## 3. 总体架构

### 3.1 三层知识模型

```
kb/                          ← 整个知识库是一个 Git 管理的 Markdown Vault
├── raw/                     ← 【原料层】人上传/编写的原始文档，不可变语义
│   ├── 财务/2024年报.md
│   └── originals/           ← PDF 等原始格式，供页码溯源与复核
├── wiki/                    ← 【编译层】agent 维护的综合知识，Markdown 页面
│   ├── index.md             ← 全库总目录（LLM 导航入口）
│   ├── log.md               ← 追加式审计日志
│   ├── sources/             ← 每个 raw 文档一页导读（摘要+示例问题）
│   ├── entities/            ← 实体页
│   ├── concepts/            ← 概念页
│   ├── synthesis/           ← 主题综合页（懒更新）
│   └── answers/             ← 问答回流页
├── AGENTS.md                ← 【契约】agent 维护本库的工作规范
└── .index/                  ← 【缓存层】全部派生、可重建
    ├── tree.db              ← 文档树（Section/Block 结构）
    ├── vec.db               ← 向量索引
    ├── fts.db               ← 全文倒排（BM25）
    └── graph.db             ← 实体表 + 链接图（PPR）
```

三层之间是**单向派生**关系：`raw/` 与 `wiki/` 是真相源（均为 Markdown），`.index/` 的一切（含实体表与图）都能从这两层重建。编译层的实体页反过来又是实体表的来源——**机器索引是人读 Markdown 的投影，而非独立维护的第二套数据**。

### 3.2 架构总图

```
                        ┌────────────── 摄入链路 ──────────────┐
                        │                                      │
 输入源                 │  格式适配层    结构解析    索引构建    编译步骤  │
 MD / PDF / DOCX / Web ─┼─→ parse() ─→ 文档树 ─→ Block ────┐  │
                        │   (PDF 走    切块      向量化     │  │
                        │   双档回退)              │        ▼  │
                        │                          │   受影响面计算 │
                        │                          │   页面补丁生成 │
                        │                          │   矛盾检测    │
                        │                          ▼        │  │
                        │                     .index/    wiki/  │
                        └──────────────────────────────────────┘
                                        │
                        ┌────────────── 查询链路 ──────────────┐
                        │                                      │
 用户问题 ─→ Planner ─→ │ Router 五通道：                       │
   ▲                    │  ⓪ wiki 优先（编译层直接命中）         │
   │                    │  ① 树搜索导航（逐层是/否判定）         │
   │                    │  ② 混合召回（向量+FTS，RRF 融合）      │
   │                    │  ③ 实体图扩展（PPR 加成）              │
   │                    │  ④ 全量模式（小语料整树注入）          │
   │                    │      ↓ Rerank → Grader 充分性判断     │
   │                    │      ↺ 不足则带诊断改写，最多 N 轮      │
   └── LLM 生成 ←────── │ 上下文组装（预算纪律+向上扩展）        │
     （引用契约）        └──────────────────────────────────────┘
                                        │
              lint 园丁（定期）←──────────┘
              断链/失效/矛盾/漂移 → log.md + 修复队列
```

### 3.3 一图看懂与纯 RAG 的区别

| | 纯 RAG | KoiosBase |
|---|---|---|
| 存储 | 扁平 chunk 池 | 三层知识模型（原料/编译/缓存） |
| 查询 | 单次向量检索 | 五通道导航 + 充分性迭代 |
| 知识增长 | 只进不出 | 摄入编译 + 问答回流 + lint 自愈 |
| 错误修正 | 重切重嵌 | 状态标记 + 沿引用链级联传播 |
| 信任机制 | 相似度分数 | 引用契约 + 页码级溯源 + 质量抽检 |

## 4. 数据模型

### 4.1 文档树与 Block

文档解析为树，**Block（语义原子块）是唯一存储单元**：

```yaml
Block:
  id: "财务/2024年报.md#负债分析/块3"    # 标题路径 + 序号，人类可读
  type: paragraph | table | code | list | figure
  breadcrumb: "2024年报 > 财务分析 > 负债分析"   # 参与嵌入与组装
  raw: "..."                              # 原文；表格/代码作为整体，永不拆散
  page_range: [12, 13]                    # PDF 来源专属：页码级溯源
  content_hash: "..."                     # 节级哈希，驱动增量更新
  meta: { created, version, ttl, acl }
Section:
  id, parent_id, title, summary           # summary 为"导航式摘要"（见 5.3）
Document:
  path, frontmatter, children
```

设计要点：
- **导航式摘要**：Section 摘要不写"本节讲了什么"，而写"本节回答什么类型的问题、涉及哪些实体"——摘要服务于检索时的下钻判断，而非人类阅读概括；
- **面包屑注入**：每个 Block 参与嵌入的文本 = `breadcrumb + raw`，解决指代悬空；
- **多粒度是视图**：事实查询命中 Block，组装时向上扩展到父 Section；汇总查询直接检索 Section 摘要层。存最细，取任意粗。

### 4.2 frontmatter 规范

```yaml
---
title: 2024年度报告
source: originals/2024年报.pdf      # 原始文件（如有）
parser: mineru-2.5                   # 解析器及版本（便于定向重解析）
doc_hash: sha256:...
version: 3
supersedes: 财务/2024年报-v2.md       # 版本链
valid_from: 2025-03-01
ttl: 730d                            # 可选：时效声明
acl: [finance-team]                  # 可选：权限（v1.0）
status: active                       # active | superseded | retracted
---
```

### 4.3 wiki 页面类型与模板

编译层五类页面，统一模板纪律：**每个事实断言必须带 wikilink 到 raw 层**。

```markdown
---
type: entity                         # entity | concept | source | synthesis | answer
entity_id: acme-corp
aliases: [ACME, 艾克米]
confidence: draft                    # draft | medium | high（质量门，见 8.4）
sources: ["raw/财务/2024年报.md#负债分析"]
last_compiled: 2026-09-20
stale: false
---

# ACME 公司

## 关键事实
- 2024 年营收 32 亿元 [[raw/财务/2024年报.md#负债分析]]

## 关系
- supplies → [[entities/b-corp]]

## 矛盾与未决                       ← 摄入/查询/lint 发现的冲突固定挂这里
- ⚠️ 营收口径：年报 32 亿 vs 新闻稿 35 亿
```

各类型职责：
- `sources/`：每篇 raw 文档一页——导读摘要 + "本文档能回答的示例问题"（既助人也供查询意图匹配）；
- `entities/`：人、组织、产品等具名实体，是冲突与修正的锚点；
- `concepts/`：跨文档术语与方法论；
- `synthesis/`：跨文档主题综合，成本最高，**懒更新**（标 stale 后等查询触发重编）；
- `answers/`：问答回流页（见 6.6）。

### 4.4 AGENTS.md 契约

Vault 根部的 `AGENTS.md` 定义 agent 维护本库的完整规范：页面模板、命名规则、摄入/查询/lint 工作流、质量门标准。维护行为不藏在代码里，而是**写在库里、可读可改可版本化**；同时它也是外部 agent 经 MCP 接入时的"使用说明"（见第 11 章）。

## 5. 摄入管线：从文档到知识

摄入分三个阶段：**适配 → 索引 → 编译**。索引是同步的（查询立即可用），编译是异步的（知识积累可以晚几分钟，但绝不阻塞可用性）。

### 5.1 格式适配层

统一抽象 `parse(path) -> StructuredDoc`，**多一种格式 = 多一个适配器，主架构零改动**：

| 输入 | 适配策略 |
|---|---|
| Markdown | 原生直通；标题即树（对"加粗冒充标题"的脏文档回退到语义分段+伪标题） |
| PDF | **双档回退**（✅ 已实装）：CPU 档用 **MuPDF** 抽文本层；页面被判为扫描件（文本层为空或过短）时升级 **VLM 档**——由调用方提供的回调接收 PNG 字节并转写。抽不到且未给 VLM 时该页**跳过**而非编造。Block 记录 `page_range`；解析结果按内容哈希缓存。⬜ 尚未做：书签/大纲作为文档树骨架、图片抽取进 `assets/` |
| 扫描件 | ✅ VLM 转写路径已通（`extract_pages(path, vlm)`）；⬜ frontmatter 标记 `ocr: true` 与答案侧"源自扫描件"提示未实装 |
| DOCX / 网页 / 音视频 | ⬜ 未实装。`ingest::is_supported` 目前放行 `.md` 与 `.pdf` |

解析产物是普通 Markdown，与人手写的文档**地位完全平等**——人可以直接修改解析产物修正解析错误，节级哈希驱动增量重嵌，修改即生效。

**VLM 质量抽检环**（多模态底座的第一个用途）：解析工具可能静默篡改数字（表格合计、财报数据），因此随机抽取含表格/数字的页面，将原页截图与解析出的 Markdown 交给多模态 LLM 做一致性比对，不一致进人工队列。抽检比例可配（默认 5%，财务类建议 100% 表格页）。

### 5.2 索引构建

四个索引同时构建，服务不同查询意图：

| 索引 | 内容 | 服务的查询 |
|---|---|---|
| 文档树 | Section 层级 + 导航式摘要 | 汇总型、导航型、"库里有啥" |
| 向量索引 | Block 级嵌入（breadcrumb+raw） | 语义模糊召回 |
| FTS 倒排 | BM25 | 精确匹配：编号、型号、专名 |
| 链接图 | wikilink + 实体共指 + 结构包含 + 版本链 | 实体扩展、PPR 排序 |

**链接图的边定义**（PPR 的基础，全部从 Markdown 推导）：

| 边类型 | 来源 | 权重 |
|---|---|---|
| 显式链接 | `[[wikilink]]`、锚点引用 | 高 |
| 实体共指 | 两块提及同一实体 | 中 |
| 结构包含 | 树父子节点 | 低（主要用于向上扩展） |
| 版本链 | 新旧版本互指 | 不传分，仅用于去重与级联 |

### 5.3 编译步骤（核心算法）

编译是 KoiosBase 区别于检索式系统的关键：**把跨文档知识在摄入时物化**。规模化的关键在于——**编译 agent 从不全局扫描，受影响面靠索引计算**，成本为 O（受影响页面数） 而非 O（库规模）：

```
ingest_compile(new_doc):
    # ① 常规索引（同步）
    blocks = parse_and_index(new_doc)

    # ② 受影响面计算（索引查询，无全局扫描）
    entities_touched = entity_table.lookup(extract_entities(blocks))
    concepts_touched = vec_search(wiki_page_summaries, blocks, top_k=10)

    # ③ 补丁式更新（diff，不是重写；尊重人工编辑）
    for page in entities_touched + concepts_touched:
        patch = LLM(current=page.content, new_evidence=blocks)
        apply_patch(page, patch)          # git 可审计

    # ④ 矛盾检测：新事实 vs 页面既有断言
    conflicts = detect_conflicts(blocks, pages)
    for c in conflicts:
        page.section["矛盾与未决"].append(c)   # 挂锚点，不裁决

    # ⑤ 受影响页面重新进索引；synthesis 页标 stale（懒更新）
    reindex(touched_pages)
    log.md.append(compile_record)
```

工程属性：
- **可降级**：编译失败/延迟不影响查询（索引层已可服务）；
- **成本可控**：编译可用更小的模型；批量、异步、有预算上限；
- **增量**：文件被编辑后按节哈希只重嵌变化的节，编译也只波及受影响页面；
- **学术佐证**：WiCER（arXiv:2605.07068）证实"盲目编译"在规模扩大后因注意力稀释而完全失效——受影响面索引化（而非全库重编译）正是对这一已知失败模式的针对性设计。

### 5.4 防污染质量门

编译层是 agent 的领地，实行晋升制，防止"AI 自产内容喂 AI"的劣化循环：

- 新编译页 `confidence: draft` 起步；
- 晋升条件（任一）：**通过 L2 异族抽检**（§10.3）/ 人工确认。**引用计数不是晋升条件**——它与 PPR 权重同源相长，draft 页可借引用量自我抬升为权威（自我强化回路）；引用计数仅作 lint 的排序信号：高引用的 draft 页优先送检；
- `draft` 页检索降权但可用（不浪费，不轻信）；
- `answers/` 回流页永远从 draft 起步。

**注意**：质量门防的是"污染扩散"，防不住"生成者与判定者同源的一致性共谋"——后者由 P7 与 §10.3 的验证者多样性机制解决。

## 6. 查询管线：检索即导航

### 6.1 Router 五通道

查询不是"去向量库要 top-k"，而是 Router 按意图选择通道：

| 通道 | 机制 | 适用意图 |
|---|---|---|
| ⓪ wiki 优先 | 读 `index.md` → 命中编译页 | 跨文档综合、实体关系、概念解释 |
| ① 树搜索导航 | LLM 逐层"该子树值得展开吗"判定 | 单文档深挖、已知位置的导航 |
| ② 混合召回 | ⚠️ 设计是"向量 + FTS，RRF 融合"；**v0.8 实装为纯 FTS（BM25）**，RRF 融合保留用于通道间合并。向量一侧缺位，见 §12 |

| ③ 实体图扩展 | 实体 → 关联实体 → PPR 加成 | 多跳推理 |
| ④ 全量模式 | 语料 < 阈值（如 20 万 token）时整树注入 | 全局综诉、跨文档比较、高风险精读 |

通道不互斥：Grader 判断一条路没走通就换路或叠加。

**v0.8 落地校正**：此处的 ① 在实现里是**关键词命中 heading 路径**，不是 LLM 逐层
判定；② 无向量一侧。这两处偏离都记录在 §12。默认形态刻意不包含任何模型调用
——这是设计选择，不是未做完。

### 6.2 Planner–Grader 迭代循环

```
query(question):
    state = Planner.analyze(question)     # 意图分类 + 约束拆解（正/负约束清单）
    for round in range(MAX_ROUNDS=3):
        plan   = Router.route(state)      # 选通道
        cands  = retrieve(plan)           # 通道执行
        cands  = rerank(question, cands)  # cross-encoder 精排
        verdict = Grader.judge(state, cands)
        # verdict ∈ {enough, missing(缺什么), conflict(类型), evidence_absent}
        if verdict.enough: break
        state = Planner.rewrite(state, verdict)   # 带诊断改写
    context = assemble(cands)             # 见 6.4
    return generate(question, context)    # 见 6.5
```

关键设计：
- **Grader 取代固定 top-k**：不是"捞 5 条就答"，而是"判断够不够、缺什么、往哪补"；简单问题一轮即走，复杂问题自然多轮；
- **约束逐项核查**：Planner 把复合查询拆成正/负约束清单，Grader 逐项核对证据，而非整体问"相关吗"——细粒度差别（尤其否定与情态）在这一层被显式检查；
- **Grader 与生成模型异族**（P7）：充分性判定是与生成同源的"自证"高发区，Grader 强制使用与生成 LLM 不同家族的模型（见 §10.3）；
- **成本自适应**（Self-Route 模式）：默认检索优先；Grader 返回 `evidence_absent` 且语料规模允许时，自动升级全量模式兜底——以最小成本换取最接近全量阅读的效果。

### 6.3 排序融合：PPR 作为图信号

链接图上使用 **Personalized PageRank**（而非全局 PageRank）：以召回候选为种子做个性化随机游走，让"与候选证据在图上邻近"的节点获得加成。全局 PageRank 只以极小权重作为静态权威度兜底（解决新文档冷启动）。

```
final = α·向量相似 + β·BM25 + γ·PPR + δ·时效衰减 + ε·静态权威度
        （γ 建议 0.1~0.15：图信号做加成，不做主导）
```

实现：邻接表存 SQLite；只对候选（top 50）及其两跳邻居的子图做幂迭代，numpy 即可，毫秒级。单文档出边权重设上限防刷链。

### 6.4 上下文组装与预算纪律

- **向上扩展**：命中 Block 时附带父 Section 摘要与兄弟标题，少量 token 换完整语境；
- **预算硬上限**：组装上下文不超过模型标称窗口的 20~40%（规避 context rot——长窗口中段的内容利用率会非线性劣化），超出则摘要压缩而非继续塞；
- **缓存友好排序**：稳定内容（系统提示、文档树目录）在前，动态内容（命中块）在后，最大化 prompt 缓存命中；
- **原模态回取**：命中含图 Block 时，原图随上下文一并给多模态 LLM（见第 7 章）。

### 6.5 生成契约

生成层遵守三条硬契约（对应 P6）：

1. **引用契约**：每个事实性句子必须携带引用，穿透编译层直达 raw 层 Block（wiki 页只作导航入口，不作最终引用）；PDF 来源引用精确到页码；
2. **拒答契约**：证据不足时明确回答"资料中未涉及"，禁止用参数知识补全——LLM 在证据不足时倾向硬答且自信度失真，此契约是对抗该倾向的架构手段；
3. **冲突呈现协议**：证据冲突时**不裁决、并列呈现**，附来源、时间、版本（"来源A（2024年报 v3）称 X；来源B（2025-03 新闻稿）称 Y，差异或在统计口径"）。

### 6.6 答案回流：知识的复利

```
用户认可的回答 ─→ 保存为 wiki/answers/ 页（draft）
                ─→ 引用自动写作 [[wikilink]]
                ─→ 走正常摄入：进索引、进图、可被编译层引用
```

问答产出带完整出处链回流，PPR 图因此自动强化被频繁引用的权威文档——**知识沉淀与图排序形成正循环**。这是"知识库越用越聪明"的机械保证，而非口号。

**但正循环必须上锁**：PPR 边权重 × 源页置信系数（draft = 0，medium = 0.5，high = 1）——未晋升页的引用**不传权威分**，切断"引用量 → 权威 → 更多引用"的自我强化回路；页面晋升后其出边权重自动恢复。正循环只对验证过的知识开放。

## 7. 多模态：双轨制

多模态 LLM 是算力底座，但**不让多模态进入检索表示层**：

- **摄入时**：图片/复杂表格由 VLM 生成描述性 caption 写入 Block（可嵌入、可检索），原图存 `assets/`；树节点类型扩展为 `text | table | figure`；
- **检索时**：一切走文本通道（caption 即检索代理），不引入多模态向量——消融研究表明按模态分别处理优于统一向量空间，且成本低得多；
- **生成时**：命中的 Block 若引用图片，**原图与文本一起喂给多模态 LLM**——caption 只是代理，细节（图表数值、架构连线）必须读原图；
- **进阶（可选）**：对版式复杂的 PDF，树搜索导航可直接在页面截图上由 VLM 执行，绕开解析失真。

原则一句话：**检索用文本代理，理解用原始模态。**

## 8. 知识健康系统

知识会过时、会出错、会互相矛盾。KoiosBase 按"**检测 → 分类 → 传播 → 呈现**"四步处理，对应 P5。

### 8.1 检测：四路信号

| 时机 | 机制 |
|---|---|
| 摄入时 | 版本链 supersede；编译步骤矛盾检测；SimHash 近重复 |
| lint 时 | 失效断言传播、矛盾聚类、TTL 到期、断链扫描（见 9.3） |
| 查询时 | Grader 发现证据冲突 → 不硬答，且把矛盾**写回** wiki 页「矛盾与未决」 |
| 用户反馈 | 纠错入口 → 记 log.md → 触发定向 lint |

查询时回写是低成本高回报的闭环：矛盾常在回答具体问题时才暴露，发现一次即永久标记。

### 8.2 分类：四种"病"四种药

冲突研究的关键结论：**冲突类型决定应对策略，且类型识别不应交给现场推理**。KoiosBase 在库内显式标记类型：

| 类型 | 定义 | 处置 |
|---|---|---|
| 过时 | 曾经正确，已被更新 | 版本链：旧版 `superseded`，检索默认过滤，引用带版本/时间 |
| 错误 | 从来就是错的 | 标 `retracted`，触发级联（8.3） |
| 冲突 | 多来源各执一词 | 不裁决，并列呈现；挂实体页「矛盾与未决」 |
| 存疑 | lint 抽检发现漂移 | 降权 + 置信标注 |

### 8.3 传播：错误的影响面是可计算的

这是三层模型带来的独有能力。一个 Block 被标 `retracted` 后：

```
Block 标记 → wikilink 反向索引查出全部引用者（实体页/概念页/answers 页）
          → 引用者自动标 stale → 异步重编译 → log.md 记录传播链
```

纯 RAG 中错误 chunk 只影响自身；KoiosBase 中"这处错误污染了哪些知识"是一次确定性的图查询。修正因此可以**精确手术**而非全库重建。

**查询时的状态处置规则**（synthesis 懒更新场景的必需补丁——标记了 stale 不等于查询知道怎么用）：

| 页面状态 | 查询处置 |
|---|---|
| active / high | 正常使用 |
| draft | 降权可用，回答中显式标注置信 |
| stale | 降权 + 标注"此页待更新"；Grader 优先改走原始证据通道（②③）；查询结束后触发异步重编。**例外**：高风险领域（医疗/法律/财务）或该页为唯一证据源时——拒用该页并说明理由，或触发**限域当场重编**（仅重编该页，非全库） |
| superseded | 默认过滤；仅在用户显式查询历史版本时可见 |
| retracted | 硬过滤，绝不进入上下文；仅审计视图可见 |

原则：stale 的默认处置是"**降级绕行 + 异步修复**"，不是当场重编——当场全量重编会把懒更新省下的成本以查询延迟的形式还回去；当场重编仅限单页限域触发。

### 8.4 细粒度表述差别的分层防线

承认一个事实：**没有任何单层能防住所有细粒度差别**。按差别类型分层设防：

| 差别类型 | 例子 | 主防线 |
|---|---|---|
| 词汇/符号级 | A100 vs A100X、条文编号 | FTS 精确通道 |
| 时间/版本级 | 2023 vs 2024 收入 | 元数据过滤（不靠语义） |
| 实体级 | 同名不同物 | 实体表消歧 + 面包屑 |
| 否定/极性 | "支持" vs "不支持" | cross-encoder reranker |
| 情态/程度 | "应当" vs "可以" | LLM 读原文（最终防线） |
| 立场/口径 | 含税 vs 不含税 | 冲突呈现协议 |

两条落地纪律：
- **reranker 按场景选型**：不同 reranker 的失败模式不同（有的擅长否定却栽在情态），法律/医疗等情态敏感场景须专项测评后选型；
- **最终防线是架构性的**：向量只召回候选，判断永远由 LLM 读原文做出；高风险场景直接走全量模式。

### 8.5 生成层的时效纪律

涉时效事实的回答必须带"截至"声明（引用自带时间戳，零成本）；一切修正走 Git 历史，可回滚、可审计。

## 9. 治理与生命周期

### 9.1 版本与去重

- **版本链**：同路径新版进来，旧版标 `superseded` 不删除；检索默认 `active`，引用附版本号；
- **SimHash 近重复**：摄入时检测，近重复块指向主副本，索引只存一份；
- **TTL**：frontmatter 声明时效，到期自动降权并提示复核。

### 9.2 权限（v1.0）

ACL 写在 frontmatter，**检索前过滤**（不是生成后遮掩），多租户场景的泄露风险在召回层即被切断。

### 9.3 lint 园丁

定期体检，**增量 + 抽样**（全局扫描是规模化的敌人）：

| 检查项 | 机制 | 频率 |
|---|---|---|
| 断链/孤儿页 | 遍历链接图 | 每次编译后顺带 |
| 失效断言 | 版本链传播 | 版本变更时触发 |
| 矛盾积累 | 跨页断言聚类 | 每周 |
| 漂移抽检 | wiki 断言 vs 原始 Block 一致性（复用 VLM 抽检环；**判定模型须与编译模型异族**，见 §10.3） | 每周抽样 |
| 无源断言 | 扫描 wiki 页无引用的事实句 | 每周 |

修复分级：低风险（断链、格式）自动应用；高风险（改断言、删内容）进人工确认队列。全部记 `log.md`。

## 10. 可观测性与评测

### 10.1 全链路 Trace

每次查询落库：意图判定、通道路由、每轮召回 ID、Grader 结论与改写记录、组装内容、引用清单。bad case 可归因到具体环节（召回漏了？排错了？生成忽略了？），告别"调参玄学"。Trace 给机器归因，`log.md` 给人阅读，二者互补。

### 10.2 评测基线

**评测集与 v0.1 同时落地，先于任何优化**——没有基线的优化等于盲飞：

- 规模：首批 ≥200 题，覆盖四类：事实题、多跳题、汇总题、**细粒度区分题**（否定/数字/情态/同名实体），外加拒答题；
- 核心指标：答案准确率、**引用覆盖率**（带引用的事实句占比）、拒答正确率、召回归因分布；
- 每次解析器升级、模型更换、参数调整，跑同一评测集回归。

### 10.3 反自证：验证者多样性（P7 落地）

系统的可信度高发于"判断"环节。若编译、Grader、lint 抽检全部由同一模型家族既生成又判定，则整条链退化为"用 A 检验 A"。按 P7，验证分三级，**能用低层就不用高层**：

| 级 | 机制 | 应用点 |
|---|---|---|
| L1 程序化检查（无模型） | wikilink 目标存在性、frontmatter schema 校验、引用覆盖率正则统计、表格数字的确定性比对（解析两侧数字集合做 diff）、**时效冲突判定（版本链/TTL 元数据直接给出，无需模型）** | lint 默认项，零成本每次跑 |
| L2 异族模型判定 | 判定模型与生成模型**强制不同家族**：编译 patch 由 A 族生成 → 一致性判定由 B 族；Grader 与回答生成异族；VLM 数字抽检的模型 ≠ caption 生成模型；**冲突类型识别（§8.2）中无法程序化的部分（观点/事实冲突）走此级**；可用 NLI/entailment 专用小模型做"断言 vs 原文"蕴含判定 | 编译抽检、Grader、漂移抽检、冲突分类 |
| L3 人与外部 grounding | 双模型判定分歧自动进人工队列；每周人工抽检 1% 编译页；评测 golden set 由人构建，禁止 LLM 生成题目自评 | 分歧仲裁、定期审计、评测基线 |

落地成本可控：判定类调用（充分性、一致性、蕴含）输出短、可用小模型或便宜 API；异族配置只需在模型路由层加一条"角色 → 允许模型族"的绑定表。

该三级结构与 WiCER（arXiv:2605.07068）的核心结论一致：编译必须带 **evaluate + refine** 环节，无评估的编译在规模下失效——L1/L2 即 KoiosBase 的 evaluate，分歧升级与重编译即 refine。

---

## 11. 外部接口

- **MCP Server**：KoiosBase 把自身暴露为 MCP 工具（检索、问答、写入），接入外部 agent 生态；`AGENTS.md` 即接入说明；
- **MCP 消费**：外部数据源（工单、IM、网盘）经 MCP 适配进入摄入管线；
- **记忆边界**：KoiosBase 管理**语义知识层**（共享、策展、可审计）；会话记忆、用户偏好等情景记忆属于 agent 侧，**不回流入库**——防止临时状态污染知识。

## 12. 技术选型与资源估算

落地状态一栏用 ✅ / ⬜ 标注：**✅ = v0.8 的 Rust 二进制里已实装**；⬜ = 设计保留、
尚未实装。此表随代码更新，不是设想清单。

| 组件 | 选型 | 状态 | 理由 |
|---|---|---|---|
| 存储 | SQLite + FTS5（`rusqlite` bundled，静态编译进二进制） | ✅ | 零部署，一个文件即整个库。**sqlite-vec / 向量维度未引入**——见下方"v0.8 刻意未做的事" |
| 解析 Markdown | 自研 heading-stack 解析器（`lib.rs` `index_file`） | ✅ | 标题即树；脏文档按行聚合成段落块 |
| 解析 PDF | MuPDF（CPU 文本层）+ 可插拔 VLM 回调（PNG 字节） | ✅ | 双档回退已落地：`extract_pages(path, vlm)`；扫描件缺 VLM 时跳过而非编造 |
| Embedding | bge-m3 / bge-small | ⬜ | v0.8 无任何向量依赖，检索全靠 BM25 + 链接图 PPR |
| Reranker | bge-reranker 系列 | ⬜ | 同上；cross-encoder 属情态敏感场景的专项增强 |
| LLM/VLM | 可插拔回调：`LlmFn` / `VlmFn` 两个 `dyn Fn` 类型别名 | ✅ | 统一的 callable 契约；**仓库内零 provider 适配器、零 API key 配置** |
| 服务 | 无——纯本地 CLI + MCP over stdio | ✅ | 单机够用；不需要 HTTP 层就不需要它的部署面 |
| 版本管理 | Git | ✅ | 原生审计与回滚（`wiki/` 入版本库，`.index/` 永不入） |

**v0.8 刻意未做的事**（设计如此，不是漏做）：

- **向量 / embedding / reranker 全缺失。** 检索是双通道：FTS5 的 BM25（精确匹
  配：编号、型号、专名）+ 链接图上的个性化 PageRank（实体扩展）。 §6.1 的"向量
  索引"通道在设计里保留，但实现选择先用 BM25+PPR 建立可验证基线——**在无法通过
  评测证明它带来收益之前，不引入一个需要额外 1GB 驻留的依赖**。这是能力的取舍，
  不是违约。
- **§7 的"摄入时由 VLM 生成 caption"只做到一半。** 已实装的是"文本层抽不出来时把
  页面交给 VLM 转写"（`extract_pages(path, vlm)`）；caption 向量化、图片描述进
  `assets/` 尚未实装——向量层缺位，caption 无处可去。
- **被删掉的 Python 实现不再是备选之一。** 曾经"Python 参考 + Rust 移植"的双壳格局
  在 2026-10-08 结束；历史上那种"评测/生产分离"的分裂，在单一二进制下已无意义。

**资源量级**：5 万文档级，16GB 内存单机可承载索引与检索；编译与抽检为异步批处理，可用小模型。

> **v0.8 实测校正（2026-10-08）**：上面的 16GB 估算是为"embedding + reranker +
> 本地生成 LLM + NLI 判定小模型"同机驻留做的。v0.8 **一个模型都不驻留**——默认形态
> 零模型调用，LLM/VLM 完全由调用方以回调提供。因此实际运行足迹是单个 12 MB 二进制
> 加 **4 个系统动态库**（`libgcc_s` / `libm` / `libc` / 动态加载器，另有 vdso），
> 实测体积 11.8 MB。索引随库大小增长，**不存在常驻模型内存**。若日后接 embedding，
> 这条 16GB 估算重新适用。
>
> ```console
> $ ldd rust-cli/target/release/koios
>         linux-vdso.so.1
>         libgcc_s.so.1 => /lib/x86_64-linux-gnu/libgcc_s.so.1
>         libm.so.6     => /lib/x86_64-linux-gnu/libm.so.6
>         libc.so.6     => /lib/x86_64-linux-gnu/libc.so.6
>         /lib64/ld-linux-x86-64.so.2
> ```

**P7 与单机轻量的兼容性**：异族要求 ≠ 本地双 LLM 驻留。判定角色按优先级这样满足——① 小型 NLI/cross-encoder 模型（数百 MB，与生成 LLM 天然异族异构，可同机驻留）；② 便宜 API（判定类调用输出短，成本极低）；③ 第二 LLM 本地驻留（精度档，非默认）。16GB 估算覆盖：embedding + reranker + 单个本地生成 LLM + NLI 判定小模型。

## 15. 与相关工作的关系

> 本章条目已于 2026-09-28 逐项检索核实（仓库存在性、论文出处、关键主张），链接附后。具体数字类主张（如基准分数）均来自项目方或二手转引，未经我们独立复现，采纳前建议自行验证。

KoiosBase 的设计决策均有外部独立验证，但系统本身是从七条第一性原理（第 2 章）整体推导的，而非方案拼接：

- **PageIndex**（Vectify AI，[github.com/VectifyAI/PageIndex](https://github.com/VectifyAI/PageIndex)，MIT 协议）验证了"文档树 + 推理式导航"在专业文档上的有效性（官方及 arXiv 转引称 FinanceBench 98.7%）；其开源核心限于单文档、跨文档能力在商业层，查询延迟高于向量检索。KoiosBase 将树搜索作为五通道之一，并以向量/FTS/实体图补齐跨文档与延迟短板；
- **HippoRAG**（OSU NLP Group，[github.com/OSU-NLP-Group/HippoRAG](https://github.com/OSU-NLP-Group/HippoRAG)；论文 [arXiv:2405.14831](https://arxiv.org/abs/2405.14831)，NeurIPS 2024）为"PPR 跑在知识图上做多跳检索"提供了学术依据——论文摘要称多跳 QA 超越此前 SOTA 最高 20%（注：该数字出自论文摘要而非 README，属作者主张，未经我们复现）；KoiosBase 用 Markdown wikilink 建图，免去重型图谱工程；
- **LLM Wiki**（Andrej Karpathy，2026 年 4 月，[gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，arXiv 论文题注为 *LLM Wiki: A Second Brain for LLM Agents*）确立了"编译而非检索"的范式与 Ingest/Query/Lint 三操作。**需要诚实说明**：本文档"知识即构建"的软件工程隐喻（源码/编译产物/CI 的映射）与社区对该 gist 的主流解读收敛，并非 KoiosBase 独创；我们的增量贡献在于——用索引计算受影响面解决其社区报告的数百页后导航退化问题、以引用穿透+VLM 抽检治理编译层漂移、以及编译层与工程化检索层的完整结合。该范式已有学术跟进，其中 **WiCER**（[arXiv:2605.07068](https://arxiv.org/abs/2605.07068)）的实验结论尤为重要："盲目编译（blind compilation）完全失效、规模扩大后注意力稀释"——这从学术上独立印证了 KoiosBase 的两处核心设计：受影响面索引化（§5.3）与"编译必须带评估-精炼环"（P7 / §10.3），方向仍在快速演化；
- **NotebookLM**（Google）验证了"来源约束 + 引用审计 + 输出沉淀"的产品范式；KoiosBase 的笔记回流与其同构，但凭借 wikilink 图实现知识复利，且引用精确到标题路径与页码；
- **Contextual Retrieval**（Anthropic，2024 年 9 月，[anthropic.com/news/contextual-retrieval](https://www.anthropic.com/news/contextual-retrieval)，官方称检索失败率降 49%、加 rerank 达 67%）验证了上下文注入的收益——KoiosBase 的面包屑注入与之同思路、零 LLM 调用成本；
- 2026 年行业共识（混合架构、记忆分层、文本代理多模态、评测基线）与本文档第 6/7/10/11 章一致。

**一句话定义**：

> KoiosBase 把知识库当作持续构建的软件工程：Markdown 是源码，编译层在摄入时完成综合，索引是可重建的构建产物，lint 是持续集成，Git 是版本控制——检索只是这个工程的运行时之一。
